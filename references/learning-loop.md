# 经验迭代与共同维护

适用：本技能执行中出现新困难、新控件行为、用户新教法或新的有效解法。

## 本地闭环

1. **先接续，再定位。** 读当前任务记录和相关案例，确认文章、版本、已保存位置和当前问题。优先复用同一环境中已有的成功方式。
2. **记录最小事实。** 写下可观察现象、当时的焦点/选区/容器层级、使用的控件和反馈。原因尚待验证时使用“可能原因”或“待验证”。
3. **一次验证一个判断。** 对最小范围尝试修正，读回状态，再决定下一步；修正前保留必要恢复点。反复出现相同反馈时，调整诊断信息和假设。
4. **验证真实结果。** 文字用全文或段落回读，样式用实际值和视觉检查，滑动用逐页身份检查与双向操作，保存用重新加载。记录验证的环境和范围。
5. **写进已有参考。** 相同问题补充原案例，新问题增加简洁条目。优先修改对应操作段落；较长案例单列参考并从入口链接。已验证解法与待验证建议分别标记。
6. **保留可迁移条件。** 保存控件名称、选择层级、判断依据和结果。公开案例使用角色名称和中性操作场景；具体人员、项目、活动、组织、栏目及群体标识留在原始任务记录中。坐标、标签ID、数量和色值按当前页面重新确认。
7. **同步与检查。** 在当前用户已授权维护技能的范围内，更新技能源码、安装副本和现有任务记录；按下文同步工具检查差异与逐文件一致性，公开反馈依当前使用者的明确选择执行。历史版本按项目Git规则留存，清理本轮临时材料。交付时区分本轮新增、已有方法复用及未验证尝试，分别说明源码、安装版、仓库的实际状态。

## 案例最小格式

```text
标题 / 日期：
来源类型：用户明确教法 / 实际操作验证 / 范例归纳
适用场景与环境：
观察到的现象：
原因或待验证判断：
有效步骤：
结果与验证证据：
适用边界：
下次可提前做的检查：
```

失败尝试只保留对下一次选择有帮助的结论。工作流设计建议标记“流程建议”，实际成功操作标记“已验证”。由单次案例得出的步骤，随下一次使用再次检查页面和条件。

## 公开贡献

仓库的 README、技能和贡献指南明示经验回馈流程，使用者自愿参与。建议在遇到有复用价值的问题后，提供“现象—步骤—验证—适用范围”，通过 Issue 讨论，再通过 PR 更新对应参考。

### 每位使用者独立选择

当前使用者尚未表态且本次有值得反馈的经验时，专门询问：

> 你是否愿意把本次使用中遇到的困难、修复步骤和验证结果，整理成脱敏经验，提交到 [技能仓库](https://github.com/854259/xiumi-article-layout-skills) 用于改进？只提交通用方法，原稿、图片、身份资料和账号信息保留本地。

提供“愿意反馈”和“不反馈”两个清楚的选择。明确同意后，整理经验并通过当前账号有权限的 Issue、PR 或维护者同步方式执行，回读提交结果；不同意就跳过公开反馈，照常完成当前任务，不反复劝说。未回答时保持未授权状态。首次询问后可在使用者本地保存选择，授权范围不变时沿用；用户随时可以撤回。选择不写入公开技能、示例配置或他人的安装包。克隆、安装及使用本技能本身不代表同意反馈。

- 发布内容以通用方法和最小可复现实例为主；人物素材、原稿、私人路径、账户信息、临时预览凭证及私聊保留在各自本地资料中。
- 发起 Issue、PR、提交或推送前，按当前用户对具体仓库和内容的授权执行；拉取、安装与日常使用仅开展已授权的任务。
- 仓库经验经维护者检查证据、适用条件与表达后合并。读者根据自己的当前需求决定采用哪些方法。
- 本技能通过可见文字指导任务后的复盘与维护；本地写入、远程发布和定时执行分别由对应环境及用户授权驱动。

新增案例同时检查三件事：是否复现了问题，解法是否验证了实际结果，通用规则是否保持了原任务范围。

## 可执行同步

同步随技能维护任务执行，由当前执行者调用；无需后台常驻。每次任务收尾先判断有没有新经验，有则在已有参考中合并，随后检查并同步。源码是编辑入口；安装版若有独立修改，先保留并合并回源码。远程出现其他更新时，保留当前结果，核对和合并后再发布。

附带 [sync_skill.py](../scripts/sync_skill.py) 使用 Python 3 标准库和 Git。运行时默认读取该技能目录下的 `.sync.local.json`，也可显式传入 `--config`。本地配置指向源码、安装目录、独立发布 Git 元数据和外置状态文件；这些文件不进入公开清单。

```text
python scripts/sync_skill.py --config <本地配置路径>
python scripts/sync_skill.py --config <本地配置路径> --apply
python scripts/sync_skill.py --config <本地配置路径> --push
```

- 默认检查并列出差异；`--apply` 同步运行所需文件到安装目录并回读SHA-256。
- `--push` 同步安装并发布通用技能清单；配置必须有当前使用者对该仓库的明确同意 `authorized_publish: true`。未同意时仅开展已授权的本地工作。
- 使用独立发布Git历史、明确仓库和分支；先核对远程与上次基线，再普通推送。远程变化、安装版独立改动或缺失基线会报告冲突，保留内容供合并。
- 首次配置时先核对现有安装文件与远程版本，再填写外置基线。对已确认不存在的新增运行文件使用null；基线记录的是实际已核验状态。
- 配置字段为 `source`、`install`、`git_dir`、`repo_url`、`branch`、`baseline`、`authorized_publish`。路径使用本机绝对路径；凭据使用现有Git认证，不写入配置。选择“不反馈”时设 `authorized_publish: false`，新的使用者默认保持未授权。
- 当前环境通过已配置的HTTP代理联网、而Git直连失败时，可核对实际代理后在本地配置增加 `git_proxy`；只接受不含账号密码的HTTP/HTTPS地址，并仅作用于同步进程的Git调用。具体地址由当前使用者环境确定，公开配置保持不预设代理；连接失败保留同步状态并报告实际阶段。
- 同步回报区分本地成功与远程成功；公开内容只含固定清单中的技能说明、配置元数据、脚本和测试，正文素材、截图、临时预览票据及本地选择不上传。

### 首次配置

下例为字段示意，路径和仓库需替换为当前使用者实际确认的位置；默认不授权公开反馈。安装目录下的 `.sync.local.json` 可保存该配置：

```json
{
  "source": "D:/work/xiumi-article-layout-source",
  "install": "D:/tools/skills/xiumi-article-layout",
  "git_dir": "D:/work/skill-publisher.git",
  "repo_url": "https://github.com/854259/xiumi-article-layout-skills.git",
  "branch": "main",
  "baseline": "D:/work/skill-sync-state.json",
  "authorized_publish": false
}
```

由执行者先读取 `scripts/sync_skill.py` 的 `RUNTIME_FILES` 清单，逐项计算源码和现有安装文件的SHA-256并比较；已有独立修改先合并或保存。基线的 `install` 记录当前已核验的安装文件哈希，明确不存在才记null。源码与安装暂时不同是待同步差异，后续执行默认检查时再次核对。外置状态结构如下，其中占位字符串须替换为实际值：

```json
{
  "version": 1,
  "install": {
    "SKILL.md": "实际64位SHA256",
    "agents/openai.yaml": "实际64位SHA256",
    "references/writing-and-review.md": "实际64位SHA256",
    "references/ui-workflow.md": "实际64位SHA256",
    "references/color-and-recovery.md": "实际64位SHA256",
    "references/learning-loop.md": "实际64位SHA256",
    "scripts/sync_skill.py": null
  },
  "remote_commit": null
}
```

Windows可用 `Get-FileHash -Algorithm SHA256 -LiteralPath <文件>` 读取哈希，其他环境可用Python标准库 `hashlib.sha256(Path(...).read_bytes()).hexdigest()`。仅做本地同步时，`remote_commit`可为null。准备公开同步时，通过 `git ls-remote <已确认仓库URL> refs/heads/<分支>` 取得实际提交，检查仓库与公开文件范围后填写该值。发布Git目录应是为该技能独立建立或已核实的bare仓库；新目录使用 `git init --bare <独立路径>` 初始化。首次状态文件独占创建，既有状态先检查，不覆盖其历史基线。最后运行默认检查，确认计划后再执行已授权的同步模式。

## 已验证案例：新建仓库的上传权限

- **现象与范围：** 用户已授权公开通用技能；网页成功创建公开仓库，连接器读取仓库正常，写入接口返回403及 `Resource not accessible by integration`。
- **判断：** 当前连接器的写入权限与已登录用户的仓库权限分别核对。该错误属于此连接路径的能力限制；安全审批拒绝或用户撤回授权则按其具体要求处理。
- **有效步骤：** 先确认仓库身份、公开范围与文件清单，再使用本机已配置的Git凭据管理器，单独建立本次公开文件的提交并正常推送。凭据由Git管理器处理；进程采用非交互模式，遇到认证缺口时按当前工具流程恢复。
- **验证：** 推送后回读远程分支、公开属性、许可证及完整文件树，逐文件比较Git对象哈希与大小。公开包与私人项目版本分别留存。
- **收尾与改进：** 复查远程内容后清理本轮临时发布目录。以后先核对连接器对目标仓库的写入能力，并将上传文件限制在明确的技能清单内。
